## 1. Domain Model Validation

**ISA-95 hierarchy**: Site → Line → Asset is correct for a single-site deployment. The model omits Area (ISA-95 Level 3) between Site and Line, but for 2 lines / 10 assets this is appropriate — no over-engineering.

**Gaps identified:**
- **Shift calendar table is missing.** OEE math references shift_minutes and planned_downtime, but there is no `CORE.SHIFT_CALENDAR` table. Mission 02 needs to join shift boundaries to allocate downtime by overlap. The backfill (Mission 01) must generate this table — `AGENTS.md` mentions shifts A/B/C with times but has no DDL for it. **Fix: add `CORE.SHIFT_CALENDAR (shift_date, shift_code, line_id, start_ts, end_ts, planned_minutes, planned_downtime_minutes)` to the canonical data model.**
- **Product-to-line mapping is implicit.** `PRODUCTION_ORDER.line_id` works, but there is no master product table. Not blocking — product_code as a dimension in the semantic view suffices for this scope.
- **No asset-state transition log.** `PRODUCTION_EVENT.state` captures point-in-time state, but gap-free state transition tracking (for run_time calculation) depends on contiguous rows. Mission 02's DT layer must gap-fill. This is a pipeline concern, not a model gap.
- **`PURCHASE_REQUISITION.wo_id` FK is nullable** — requisitions can be created during proposal (before WO exists) and linked at approval time. The column description says "FK" but it should be nullable FK. Confirm this is intentional.

**Verdict: Model is sound.** One structural gap (shift calendar) needs adding. No over-engineering — the 8-schema layout cleanly separates concerns.

| Mode pair | Distinguishable? | Disambiguator |
|---|---|---|
| BEARING_WEAR vs LUBRICATION_LOSS | **Ambiguous early** — both raise vibration. | Kurtosis rises first in bearing wear (impulsive impacts); lubrication loss shows temp+vibration correlated with load. Kurtosis + load-correlation features are critical. |

**Recommendation:** Mission 01 should ensure at least one hard negative where a healthy asset has correlated temp+vibration under heavy load (already specified as "hot-but-healthy"). Mission 03's classifier (if built) should report per-mode F1 with a confusion matrix — the BEARING_WEAR vs LUBRICATION_LOSS cell is the key quality signal.

## 3. Architecture Decision Records (ADR-001 through ADR-005)

### ADR-001: Dynamic Tables vs Streams+Tasks Split

**Context:** The pipeline layer (Mission 02) must transform raw telemetry through cleaning, aggregation, feature engineering, and OEE computation with <120s end-to-end latency.

**Decision:** Use Dynamic Tables for all declarative transformations (clean → 1min → 15min features → OEE marts → asset health). Use Streams+Tasks only for side-effecting operations: alert scoring (writes to ACTION.ALERT), outbox retry, and anomaly detection scoring (calls ML model APIs).

**Rationale:**
- DTs are incremental by default, self-managing, and composable — no manual watermark/offset logic.
- DTs cannot call stored procedures or have side effects — alert scoring must be a Task.
- TARGET_LAG provides declarative freshness control: 1min for sensor clean, 5min for features, downstream for OEE.
- If a DT falls back to FULL refresh, it's a correctness signal (query not incrementalizable) caught by the test harness.

**Consequences:** ~8 DTs in the pipeline; 3 Tasks (alert scoring, anomaly detection, outbox retry). The ML scoring task is the most complex — it reads DT outputs and writes to ML tables.

### ADR-002: Hybrid ML (Anomaly Detection + Classifier) vs Single Method

**Context:** The system must detect degradation 24+ hours before failure across 5 modes, with recall ≥0.8.

**Decision:** Primary: Snowflake ANOMALY_DETECTION (multi-series, per-signal). Secondary: FORECAST for trend visualization. Stretch: XGBoost classifier for mode prediction. Fallback: Z-score + persistence in pure SQL.

**Rationale:**
- ANOMALY_DETECTION is unsupervised — doesn't need labeled training data (labels used only for evaluation). Trains on healthy windows, flags deviations. This matches the "degradation ramp" physics well.
- Mode prediction (which failure?) requires supervised classification — hence XGBoost stretch goal using FEATURES tables (never ground truth as input).
- Risk fusion combines anomaly distance + classifier probability + persistence + criticality into a single health score and failure_probability_24h.
- Z-score fallback ensures the demo works even if Cortex ML is unavailable (probe-gated).

**Consequences:** Mission 03 is probe-dependent. The z-score fallback must produce the same output schema (ML.ANOMALY_EVENTS) so downstream consumers are unaffected.

### ADR-003: Propose-vs-Create Human Approval Guardrail

**Context:** An AI agent must never autonomously execute maintenance actions. The system needs a trust boundary between recommendation and execution.

**Decision:** Two-procedure separation: `PROPOSE_WORK_ORDER` (read-only, returns draft JSON) and `CREATE_WORK_ORDER` (write, requires human approver identity + ACKED alert + no duplicate + explicit dry_run=FALSE). Every state transition logged to append-only ACTION_AUDIT.

**Rationale:**
- PROPOSE has zero side effects (exception: PURCHASE_REQUISITION inserts for procurement prep — these are paperwork, not maintenance action).
- CREATE enforces 4 preconditions: alert status ACKED, approver not null/not 'AGENT', no duplicate open WO, explicit dry_run=FALSE.
- DRY_RUN defaults TRUE — accidental calls return a preview, never write.
- Append-only audit means no evidence can be deleted post-hoc.

**Consequences:** The Streamlit app's approve button must collect an approver name (typed, not selected from a dropdown of the current user — the prompt is explicit about this). The agent tool `PROPOSE_WORK_ORDER` is safe to expose; `CREATE_WORK_ORDER` is never called by the agent.

### ADR-004: GitHub Issues via MCP with OUTBOX Fallback

**Context:** Approved work orders need to sync to an external ticketing system (GitHub Issues chosen over Jira due to licensing). MCP is the preferred mechanism but may be flaky or unavailable.

**Decision:** Three-tier delivery: (1) MCP call to GitHub via the configured MCP server (attempted by the triage automation/CLI, not by SQL). (2) On failure, payload written to `ACTION.WORK_ORDER_OUTBOX` with target='GITHUB'. (3) TASK_OUTBOX_RETRY retries every 10 min, dead-letters after 5 attempts.

**Rationale:**
- MCP calls cannot be made from SQL stored procedures — they run in the CoCo CLI/automation context. So the SQL layer only prepares the payload (QUEUE_GITHUB_SYNC writes to OUTBOX); the automation leg executes the MCP call.
- Slack is simpler (HTTP via external access integration) but also gets OUTBOX fallback for resilience.
- The OUTBOX pattern ensures no approved action is silently lost.

**Consequences:** The `triage-automation.md` prompt must handle the MCP leg. If MCP is not configured (step 0.4 TODO), GitHub sync stays in OUTBOX indefinitely — the demo still works (show OUTBOX entries + "would sync when MCP configured"). Slack webhook needs an external access integration + secret.

### ADR-005: Streamlit Runtime Choice

**Context:** Mission 06 deploys a Streamlit app. Container runtime supports direct Agent REST API calls; warehouse runtime requires a stored-procedure wrapper.

**Decision:** Prefer container runtime (checked via ENV_PROBES or runtime probe). Fall back to warehouse runtime with a proc wrapper for agent calls. Record which was used.

**Rationale:**
- Container runtime: native network access, can call Agent REST directly, better for the "Ask Aegis" chat page.
- Warehouse runtime: more widely available, but agent calls must go through a SQL proc that wraps SNOWFLAKE.CORTEX.AGENT().
- The app must work on either — the agent-chat page abstracts the call mechanism behind a helper function.

**Consequences:** `app/streamlit_app.py` needs a runtime detection function and conditional agent-call logic. The proc wrapper must be created in Mission 04 or 06 regardless (fallback path).
