## Problem

Today a work order is only *approved* and queued to GitHub/Slack; its resolution depends on the local outbox dispatcher closing the GitHub Issue. In a production Snowflake environment (no outbound network from tasks, no dispatcher) the maintenance job itself — start work, do the repair, record findings and parts used, verify, close — has no home in the app. Procurement is already a separate page (mission 08); work-order execution must be a real process in the Work Order page, linked to procurement and to the schedule.

## Deliverables

1. **Lifecycle procedures** (idempotent DDL in `sql/10_action_procs.sql` or a new numbered file; same guardrails style as `CREATE_WORK_ORDER`: actor NOT IN (NULL,'','AGENT'), `dry_run DEFAULT TRUE`, audit row for every attempt including rejections, valid transitions only):
   - `ACTION.START_WORK_ORDER(wo_id, technician, note, dry_run)`: `APPROVED|SYNCED → IN_PROGRESS`. **Rejected while required parts are not available to this WO** (reserved for the WO and on hand), returning which parts/requisitions block it. Marks the linked `WO_SCHEDULE` row `IN_PROGRESS`.
   - `ACTION.COMPLETE_WORK_ORDER(wo_id, technician, finding, action_taken, labor_hours, parts_used VARIANT DEFAULT NULL (defaults to the WO's kit), outcome ('FIXED'|'PARTIAL'), dry_run)`: `IN_PROGRESS → RESOLVED`. Consumes parts exactly once (`on_hand_qty` and `reserved_qty` decrease), writes a `CORE.MAINTENANCE_HISTORY` row (finding, action, parts_used, labor_hours, technician note — this feeds future RCA/search), marks the `WO_SCHEDULE` row `COMPLETED`, records actual vs estimated duration.
   - `ACTION.CLOSE_WORK_ORDER(wo_id, approver, verification_note, dry_run)`: `RESOLVED → CLOSED` (verification note required; approver must differ from the technician), sets `CLOSE_REASON`/`CLOSED_AT`, closes the linked alert (`CLOSED`), and queues a GitHub-close + Slack message into the OUTBOX (so an optional dispatcher can mirror it; the app flow must work without any dispatcher).
   - Extend `ACTION.UPDATE_REQUISITION_STATUS` so that on `RECEIVED` the received quantity is **reserved for the linked WO** (up to its shortage), which is what unblocks `START_WORK_ORDER`.
   - `CANCELLED`/`REJECTED` work orders release reserved parts and schedule capacity (keep existing behavior and tests passing).
